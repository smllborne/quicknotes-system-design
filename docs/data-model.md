# QuickNotes Data Model

Target database: **PostgreSQL**. The model supports the API in [api-design.md](api-design.md).

## Entities

### users

| Column | Type | Key / constraint | Notes |
|--------|------|------------------|-------|
| id | UUID | **Primary key** | Generated by the app or `gen_random_uuid()` |
| email | VARCHAR(255) | UNIQUE, NOT NULL | Stored lowercase |
| password_hash | VARCHAR(255) | NOT NULL | Argon2/bcrypt hash, never the password |
| display_name | VARCHAR(100) | NOT NULL | |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | |

### notes

| Column | Type | Key / constraint | Notes |
|--------|------|------------------|-------|
| id | UUID | **Primary key** | |
| user_id | UUID | **Foreign key** to `users(id)`, NOT NULL | Owner; `ON DELETE CASCADE` |
| title | VARCHAR(100) | NOT NULL | Matches the API's 100-character limit |
| body | TEXT | NOT NULL, default `''` | Optional in the API, empty string if omitted |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | |
| updated_at | TIMESTAMPTZ | NOT NULL, default now() | |

### tags

| Column | Type | Key / constraint | Notes |
|--------|------|------------------|-------|
| id | UUID | **Primary key** | |
| user_id | UUID | **Foreign key** to `users(id)`, NOT NULL | Tags are per user, so one person's tags never leak to another |
| name | VARCHAR(30) | NOT NULL | Unique per user: `UNIQUE (user_id, name)` |

### note_tags (junction table)

| Column | Type | Key / constraint | Notes |
|--------|------|------------------|-------|
| note_id | UUID | **Foreign key** to `notes(id)`, `ON DELETE CASCADE` | |
| tag_id | UUID | **Foreign key** to `tags(id)`, `ON DELETE CASCADE` | |
| | | **Primary key** `(note_id, tag_id)` | Composite key stops duplicate links |

## Relationships

- **users to notes: one-to-many.** One user owns many notes; each note belongs to exactly one user (`notes.user_id`).
- **users to tags: one-to-many.** One user owns many tags; each tag belongs to one user (`tags.user_id`).
- **notes to tags: many-to-many.** A note can have many tags (`work`, `urgent`) and a tag can be on many notes. A relational database cannot store this directly, so the junction table `note_tags` holds one row per (note, tag) pair.

```
users 1 ──────< notes >────── note_tags ──────< tags >────── 1 users
         (one-to-many)       (many-to-many via junction)    (one-to-many)
```

## CREATE TABLE statements

```sql
CREATE TABLE users (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email          VARCHAR(255) NOT NULL UNIQUE,
    password_hash  VARCHAR(255) NOT NULL,
    display_name   VARCHAR(100) NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE notes (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID         NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title       VARCHAR(100) NOT NULL CHECK (length(trim(title)) > 0),
    body        TEXT         NOT NULL DEFAULT '',
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE tags (
    id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id  UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name     VARCHAR(30) NOT NULL,
    UNIQUE (user_id, name)
);

CREATE TABLE note_tags (
    note_id  UUID NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
    tag_id   UUID NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (note_id, tag_id)
);
```

## Indexes

```sql
-- 1. The main list query: "my newest notes first".
CREATE INDEX idx_notes_user_created
    ON notes (user_id, created_at DESC, id DESC);

-- 2. Find all notes for a tag (the junction table's primary key already
--    covers lookups starting from note_id).
CREATE INDEX idx_note_tags_tag ON note_tags (tag_id);

-- 3. Full-text search on title and body.
CREATE INDEX idx_notes_search ON notes
    USING GIN (to_tsvector('english', title || ' ' || body));
```

**Why `idx_notes_user_created`:** `GET /notes` is by far the most common request. Without an index, Postgres would scan every note of every user to find one user's notes and then sort them. With a composite index on `(user_id, created_at DESC, id DESC)`, the database jumps straight to that user's entries already in newest-first order, and it also supports cursor pagination (`WHERE (created_at, id) < (:cursor_time, :cursor_id)`). This keeps the query fast at 100 million+ rows.

**Why `idx_note_tags_tag`:** the primary key `(note_id, tag_id)` makes "tags of a note" fast, but "notes of a tag" starts from `tag_id`, which needs its own index.

## Example queries

**1. List a user's 20 newest notes (page 1)** - served by `idx_notes_user_created`:

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE user_id = :user_id
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**2. List notes with their tags (JOIN)** - used for `GET /notes` when the response includes tags:

```sql
SELECT n.id,
       n.title,
       n.created_at,
       COALESCE(array_agg(t.name) FILTER (WHERE t.name IS NOT NULL), '{}') AS tags
FROM notes n
LEFT JOIN note_tags nt ON nt.note_id = n.id
LEFT JOIN tags t       ON t.id = nt.tag_id
WHERE n.user_id = :user_id
GROUP BY n.id
ORDER BY n.created_at DESC
LIMIT 20;
```

**3. All of a user's notes that have the tag "work"** - `GET /notes?tag=work`:

```sql
SELECT n.id, n.title, n.created_at
FROM notes n
JOIN note_tags nt ON nt.note_id = n.id
JOIN tags t       ON t.id = nt.tag_id
WHERE n.user_id = :user_id
  AND t.name = 'work'
ORDER BY n.created_at DESC;
```

**4. Create a note and its tag link in one transaction** - `POST /notes`:

```sql
BEGIN;
INSERT INTO notes (user_id, title, body)
VALUES (:user_id, 'Buy groceries', 'Milk, eggs')
RETURNING id;

INSERT INTO tags (user_id, name) VALUES (:user_id, 'errands')
ON CONFLICT (user_id, name) DO NOTHING;

INSERT INTO note_tags (note_id, tag_id)
SELECT :note_id, id FROM tags WHERE user_id = :user_id AND name = 'errands';
COMMIT;
```

**5. Count notes per tag** - an analytics-style query for a read replica:

```sql
SELECT t.name, COUNT(*) AS note_count
FROM tags t
JOIN note_tags nt ON nt.tag_id = t.id
WHERE t.user_id = :user_id
GROUP BY t.name
ORDER BY note_count DESC;
```

## SQL vs NoSQL decision

**Decision: SQL (PostgreSQL).** QuickNotes data is naturally relational: users own notes, and notes and tags form a many-to-many relationship that needs joins and integrity rules (a note cannot exist without a user, a tag link cannot point at a deleted note). PostgreSQL enforces those rules with foreign keys and transactions, so creating a note together with its tags either fully succeeds or fully fails. The workload is also simple and predictable: reads and writes are scoped to a single user and served by one composite index, and our estimate of roughly 0.3 TB of new raw data a year (about 0.6 TB with indexes) (see [architecture.md](architecture.md)) is comfortably within what Postgres handles with read replicas, and later by partitioning or sharding by `user_id` if needed. A NoSQL document store (such as MongoDB) would store each note as a flexible document and scale out easily, but we would lose joins and foreign keys and would have to enforce consistency in application code; QuickNotes does not need schema flexibility or write volumes that would justify that trade. If we later add very high-volume, loosely structured data (such as activity logs or analytics events), we can store that in a NoSQL store alongside Postgres.
